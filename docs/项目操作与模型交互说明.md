# 项目操作与模型交互说明

## 1. 项目是做什么的

这个项目是一个告警接入与智能研判服务，主要职责是：

1. 接收 Zabbix 或通知脚本发送过来的原始告警。
2. 解析出主机、IP、告警类型、资源范围、阈值、状态等结构化信息。
3. 到 Zabbix 查询该告警相关的真实上下文数据。
4. 把告警和上下文一起发给火山模型做研判。
5. 根据模型返回的结果，决定是否推送、是否并单、是否转工单。
6. 把告警、模型计划、上下文、最终判断、incident、工单状态等信息存储下来。

这个服务本身不是监控系统，也不是工单系统。
它处在 Zabbix 和人工值班/工单系统之间，承担“接警、补数、研判、去重、落库”的角色。

## 2. 程序运行后的整体流程

程序启动后，整体链路如下：

1. 外部系统把告警发到本服务。
2. 本服务解析告警内容，得到标准化告警对象。
3. 本服务先把基础告警入库。
4. 本服务向火山模型发起第一次调用：
   这一步是 Planner。
   模型只负责判断“还需要哪些附加信息”。
5. 本服务根据 Planner 返回，到 Zabbix 查询对应上下文。
6. 本服务向火山模型发起第二次调用：
   这一步是 Judge。
   模型负责做最终研判，输出优先级、动作、原因、报告、建议。
7. 本服务基于数据库状态做去重、并单、恢复关闭、工单状态处理。
8. 本服务把最终决策和 AI 返回结果入库，并返回接口结果。

## 3. 与火山模型的交互关系

### 3.1 这个程序和火山模型分别负责什么

程序负责：

- 接收告警
- 解析告警
- 去 Zabbix 查准数据
- 按固定时间窗口采样历史数据
- 保存数据库
- 做 24 小时重复告警抑制
- 处理 incident、并单、恢复、工单字段

火山模型负责：

- 判断还需要哪些上下文
- 基于上下文做最终研判
- 输出优先级、动作和中文报告
- 给出处置建议

简单说：

- 程序负责“查数、控流程、落库”
- 火山负责“分析、判断、写报告”

### 3.2 火山模型不是直接读 Zabbix

火山模型不会自己去访问 Zabbix。

实际交互方式是：

1. 程序先访问 Zabbix。
2. 程序把查到的数据整理成 JSON。
3. 程序把 JSON 作为 prompt/context 发给火山。
4. 火山只根据程序给它的数据做判断。

所以这个项目的关键前提是：
程序必须把数据查准、查全、查得有时间窗口。

### 3.3 现在发给火山的数据是什么

当前已经不是只发“当前值”了。

现在的口径是：

- 以告警 `event_time` 为基准
- 向前取最近 1 小时
- 每 5 分钟取 1 次
- 共 12 个采样点

火山收到的数据通常包括两层：

1. 摘要层
- `disk_summary`
- `metric_summary`
- `memory_summary`
- `disk_io_summary`
- `availability_summary`

2. 原始证据层
- `zabbix_raw`

其中 `zabbix_raw` 里会带：

- host 信息
- item 的 `itemid`
- item 的 `key`
- item 的 `lastvalue`
- item 的 `units`
- item 的 `samples`

每个 `samples` 就是最近 1 小时内的 12 个点。

### 3.4 程序和火山的两次调用

当前对火山有两次交互：

#### 第一次：Planner

作用：
告诉程序这条告警还需要补哪些上下文。

例如：

- 磁盘告警需要 `disk_summary`
- CPU 告警需要 `metric_summary`
- 内存告警需要 `memory_summary`
- 宕机告警需要 `availability_summary`

#### 第二次：Judge

作用：
让模型基于原始告警和上下文做最终研判。

模型输出包括：

- `decision`
- `priority`
- `reason`
- `report`
- `merge_target_incident_no`

其中 `report` 里会包含：

- `summary`
- `checks_performed`
- `evidence`
- `priority_rationale`
- `recommendations`

## 4. 服务运行成功后，还需要我介入吗

正常运行后，不需要我持续人工介入。

也就是说，只要下面这些配置都正确：

- Zabbix 可访问
- 火山 API key 正常
- 数据库可用
- 告警入口接好了

那么这个程序会自己持续工作。

### 4.1 什么时候不需要我

如果只是正常运行、正常收告警、正常查 Zabbix、正常调用火山，这个服务会自动完成：

- 告警解析
- 上下文查询
- 模型调用
- 去重
- 并单
- 工单字段记录
- 数据库存储

这部分不需要我在线参与。

### 4.2 什么时候还可能需要我

以下情况可能还需要我介入做代码或配置调整：

1. 新的告警模板出现了
比如通知文案格式变了，导致解析不稳定。

2. Zabbix item key 发生变化
比如某些主机模板不再使用当前的指标键名。

3. 工单系统要正式联调
现在已经有工单字段，但如果后面要对接真实工单系统，还需要再接工单 API。

4. 火山模型输出风格需要继续优化
比如你希望报告格式更统一、建议更偏运维实操。

5. 去重规则要进一步细化
比如不同级别告警采用不同重复窗口，或者某些类型要更激进推送。

所以结论是：

- 运行起来后，不需要我日常盯着
- 但当告警类型、工单流程、模型策略发生变化时，可能需要我再做一次调整

## 5. 怎么启动这个项目

### 5.1 安装依赖

```powershell
python -m pip install -r requirements.txt
```

### 5.2 准备环境变量

```powershell
Copy-Item .env.example .env
```

然后按实际环境修改 `.env`。

### 5.3 启动服务

```powershell
python app.py
```

默认会启动在：

- `127.0.0.1:5000`

## 6. 关键配置说明

### 6.1 Zabbix

```env
ZABBIX_BASE_URL=http://169.24.2.90:80/zabbix/api_jsonrpc.php
ZABBIX_USERNAME=你的用户名
ZABBIX_PASSWORD=你的密码
USE_STUB_ZABBIX=false
```

### 6.2 火山模型

```env
AI_PROVIDER=volcengine_coding
AI_BASE_URL=https://ark.cn-beijing.volces.com/api/coding/v3
AI_API_KEY=你的火山 key
AI_MODEL=ark-code-latest
USE_STUB_AI=false
```

### 6.3 数据库存储

内存模式：

```env
STORE_BACKEND=memory
```

数据库模式：

```env
STORE_BACKEND=sql
DATABASE_URL=mysql+pymysql://user:password@host:port/db?charset=utf8mb4
```

## 7. 关键接口

### 7.1 告警接入接口

- `POST /api/v1/alerts/zabbix`
- `POST /api/v1/alerts/notification`
- `POST /api/v1/alerts/wechat`

推荐生产用通知类入口：

```json
{
  "to_user": "77301",
  "subject": "Zabbix告警通知",
  "alert_message": "/mnt/data01: 磁盘空间严重不足 (used > 90%)",
  "alert_detail": "WYY-DB09 (169.24.7.117) Problem in 2026.04.01 11:25:15",
  "event_time": "2026-04-01 11:25:25"
}
```

### 7.2 健康检查

- `GET /health`
- `GET /api/v1/system/storage`

### 7.3 数据清理接口

用于测试环境清空已落库数据：

- `POST /api/v1/system/storage/cleanup`

请求示例：

```json
{
  "confirm": "yes"
}
```

## 8. 当前数据库里存了什么

当前主要会存这些内容：

### 8.1 alert_event

保存原始告警事件，包括：

- 原始主机信息
- 原始告警内容
- `dedup_key`
- 原始 payload

### 8.2 alert_decision

保存最终决策，包括：

- `decision_type`
- `priority`
- `need_push`
- `push_suppressed`
- `dedup_window_until`
- `transfer_to_ticket`
- `ticket_status`
- `ai_plan_json`
- `context_json`
- `model_decision_json`
- `report_json`

### 8.3 incident

保存告警聚合后的事件，包括：

- incident 编号
- open/resolved 状态
- `dedup_key`
- `last_push_at`
- `push_count`
- 工单字段
- 最近一次模型结论和报告

## 9. 当前重复告警规则

同一个告警通过 `dedup_key` 做识别。

规则是：

1. 第一次收到该告警，会推送。
2. 24 小时内再次收到相同告警，不重复推送。
3. 超过 24 小时，如果该告警还没恢复，再次收到时会重新推送一次。
4. 如果收到 `resolved`，会关闭对应 incident。
5. 恢复后再次出现同类 `problem`，会重新开始计时和推送。

## 10. 目前项目的边界

当前已经完成的是：

- 告警接入
- Zabbix 查询
- 火山模型研判
- 1 小时时序采样
- 去重
- incident 管理
- 工单字段存储
- 数据清理接口

当前还没有完全做实的是：

- 真实工单系统 API 创建与回写
- 推送渠道的正式发送链路
- 更复杂的权限与审计控制

## 11. 一句话总结

这个程序本质上是一个“告警智能编排层”：

- 它替你把监控告警接进来
- 替你去 Zabbix 把相关数据查准
- 再把这些证据交给火山模型做中文研判
- 最后把是否推送、是否并单、是否转工单以及全部 AI 结果记录下来

所以服务跑起来以后，不需要我持续在线参与；
除非你后续还要新增告警类型、接真实工单系统、或者继续优化模型策略，我再介入即可。
